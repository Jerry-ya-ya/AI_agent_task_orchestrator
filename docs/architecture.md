# AI Agent Task Orchestrator — MVP Architecture

## 1. Technology choices

| Area | Choice | Why it fits the MVP |
| --- | --- | --- |
| Desktop shell | Electron | Straightforward Angular integration, one TypeScript toolchain, predictable process lifecycle |
| Frontend | Angular (standalone components) | Required by the product brief; signals keep polling/UI state small |
| Backend API | Node.js + TypeScript + Express | Fast to implement, easy to debug, and can run inside Electron's main process |
| Database | SQLite through Node's built-in `node:sqlite` | Local-first, synchronous transactions, no native addon rebuild during Electron packaging |
| Worker | In-process, single sequential worker | The MVP explicitly excludes parallel workers; shutdown is coordinated with Electron |
| Agent integration | `AgentExecutor` + `CodexAgentExecutor` | Business logic is independent of the Codex CLI and can later accept Claude/Gemini implementations |
| Git/process execution | `child_process.spawn`, argument arrays, `shell: false` | Commands are generated by backend rules; no command text is accepted from the renderer |

Runtime requirement: Node.js 22.5 or newer (the repository currently uses Node 24). The selected Electron release must include a Node runtime with `node:sqlite`.

## 2. Source layout

```text
src/
  backend/
    api/                 Express routes, validation, error mapping
    database/            schema/migrations and repositories
    services/            ProjectService, TaskService, GitService, TestService
    agents/              AgentExecutor and CodexAgentExecutor
    worker/              sequential polling/claim/execution pipeline
    runtime.ts            composition root and lifecycle
  electron/
    main.ts               starts/stops runtime and owns BrowserWindow
  frontend/
    app/
      components/        standalone feature views and dialogs with typed inputs/outputs
      app.component.*    dashboard container and workflow coordination
      api.service.ts     loopback backend client
      models.ts          shared frontend contracts
      task-view.utils.ts pure task presentation helpers
docs/
  architecture.md
```

The dashboard container owns API calls and workflow state. Presentation components never launch
processes or call the backend directly; they receive data through inputs and emit typed user actions.
The renderer never receives a generic command-execution endpoint.

## 4. State machine and worker flow

```text
TODO --atomic claim--> CLAIMED --> IN_PROGRESS --> TESTING --> IN_REVIEW
                               |              |                 |
                               +--------------+----> FAILED     +--approve--> PENDING_PUSH
                                                       |                         |
                                                       +--retry--> TODO           +--confirm Feature push--> DONE
                                                                                 |
                                                                                 +--legacy task--> PENDING_BRANCH_REMOVAL
                                                                                                      |
                                                                                approve removal ------+--> DONE
```

1. In a SQLite `BEGIN IMMEDIATE` transaction, select the highest-priority oldest `TODO` task and update it to `CLAIMED` with an `UPDATE ... RETURNING` guard.
2. Create a `TaskRun`.
3. Validate that the repository is clean, record its current branch, then create or reuse the selected Feature's shared `feature/{slug}` branch.
4. Persist the branch/workspace fields and set `IN_PROGRESS`.
5. Call `AgentExecutor.execute(task, workspace, signal)` with a backend-generated prompt and a timeout. The fixed prompt requires Codex to use `write-worklog` after implementation and available verification, then return only its canonical summary.
6. On agent success, set `TESTING`; `TestService` prefers a recognized test command and falls back to a recognized build command, using only backend-generated executable/argument lists.
7. The backend uses a valid returned canonical summary verbatim as the task branch commit message, checkpoints changes, stores the summary/base branch, and restores the original branch. Invalid or missing canonical summaries fail the task instead of generating a misleading success commit.
8. Successful verification sets `IN_REVIEW`. If neither tests nor a build are available—or a detected command cannot be started—the task still enters `IN_REVIEW` with an `UNVERIFIED` warning. Only a verification command that actually runs and returns non-zero sets `FAILED`; Git or agent pipeline failures also remain failures.
9. The Worker immediately polls for the next eligible task; review is not part of the worker loop. Earlier non-terminal tasks block later tasks on the same Feature, while another Feature may proceed.

The header pause/play control is an in-memory dispatch gate. Pause never cancels active Codex work; it prevents the Worker from claiming another task after the active pipeline finishes. Resume wakes the polling loop immediately.

Approving a Feature task moves it to `PENDING_PUSH`; it does not touch Git. Confirm push is a separate user action that rebases the shared Feature branch onto `main`, fast-forwards `main`, and pushes `main` to `origin` before marking that task checkpoint `DONE`. A rebase conflict is aborted and leaves the task in `PENDING_PUSH`; force-push is never used. The local Feature branch remains available for following tasks. Legacy tasks with no Feature retain the earlier per-task merge and explicit branch-cleanup path.

On application restart, orphaned `CLAIMED`, `IN_PROGRESS`, and `TESTING` tasks are marked `FAILED` rather than silently rerun. A user can then inspect logs and explicitly retry.

## 5. Process and security boundaries

- The API binds only to `127.0.0.1` on a dynamically assigned port.
- Electron waits for database migration, API listening, and Worker start before loading Angular.
- Electron uses `nodeIntegration: false`, `contextIsolation: true`, and renderer sandboxing; no preload injection is needed.
- In production Express serves the compiled Angular UI from the same random loopback origin. During development Electron passes the random API URL to the Angular dev page in the query string.
- Project paths are canonicalized and Git-validated by the backend.
- Git, test, and Codex executions use fixed commands plus argument arrays and never use `shell: true`.
- Authentication remains the responsibility of the installed Codex CLI; this application stores no token or password.
- The worker requires a clean checkout, switches to the shared Feature branch before Codex runs, checkpoints task changes there, and restores the original branch afterward.
- The worker never merges Feature changes into the base branch and never pushes.
- Approval changes only task state. The publish endpoint accepts no command text and invokes only backend-generated merge/push arguments after explicit confirmation in the UI.
- `CLAIMED` remains an internal atomic-lock state but is omitted from the Kanban columns.

## 6. API surface

Required routes:

- `GET /projects`, `POST /projects`
- `GET /features`, `POST /features`, `GET /branches`
- `POST /worker/pause`, `POST /worker/resume`
- `GET /tasks`, `GET /tasks/:id`, `POST /tasks`, `PUT /tasks/:id`, `DELETE /tasks/:id`
- `POST /tasks/:id/retry`, `POST /tasks/:id/approve`, `POST /tasks/:id/push`, `POST /tasks/:id/remove-branch`
- `GET /tasks/:id/runs`

Additional operational route: `GET /health`.

The Angular board polls `GET /tasks` so worker-driven state changes appear without introducing WebSockets in the MVP.

## 7. Deliberate MVP limits

- One local Worker and one task at a time.
- No automatic Feature merge or removal, PR automation, remote access, authentication, notifications, dependency graph, or cloud state. Feature-to-base merges remain manual.
- Test commands are detected from known project files; arbitrary command strings are not accepted from the UI/API. A repository with neither a recognized test nor build command goes to review with an `UNVERIFIED` warning.
- Deleting a task is blocked while it is executing or awaiting publication. Shared Feature branches are retained.
