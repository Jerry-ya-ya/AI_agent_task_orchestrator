# AI Agent Task Orchestrator — MVP Architecture

## 1. Technology choices

| Area | Choice | Why it fits the MVP |
| --- | --- | --- |
| Desktop shell | Electron | Straightforward Angular integration, one TypeScript toolchain, predictable process lifecycle |
| Frontend | Angular (standalone components) | Required by the product brief; signals keep polling/UI state small |
| Backend API | Node.js + TypeScript + Express | Fast to implement, easy to debug, and can run inside Electron's main process |
| Database | SQLite through Node's built-in `node:sqlite` | Local-first, synchronous transactions, no native addon rebuild during Electron packaging |
| Worker | In-process, single sequential worker | The MVP explicitly excludes parallel workers; shutdown is coordinated with Electron |
| Agent integration | `AgentExecutor` + `CodexAgentExecutor` | Business logic is independent of the Codex CLI and can later accept Claude/Gemini implementations |
| Git/process execution | `child_process.spawn`, argument arrays, `shell: false` | Commands are generated by backend rules; no command text is accepted from the renderer |

Runtime requirement: Node.js 22.5 or newer (the repository currently uses Node 24). The selected Electron release must include a Node runtime with `node:sqlite`.

## 2. Source layout

```text
src/
  backend/
    api/                 Express routes, validation, error mapping
    database/            schema/migrations and repositories
    services/            ProjectService, TaskService, GitService, TestService
    agents/              AgentExecutor and CodexAgentExecutor
    worker/              sequential polling/claim/execution pipeline
    runtime.ts            composition root and lifecycle
  electron/
    main.ts               starts/stops runtime and owns BrowserWindow
  frontend/
    app/                  Angular board, forms, task detail dialog, API client
docs/
  architecture.md
```

The renderer never launches processes or receives a generic command-execution endpoint.

## 3. Data model

### `projects`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK | Auto-incrementing |
| `name` | TEXT | User-facing name |
| `repository_path` | TEXT UNIQUE | Normalized absolute path to a validated local Git checkout |
| `context` | TEXT | Optional instructions passed to the agent |
| `created_at` | TEXT | UTC ISO-8601 |
| `updated_at` | TEXT | UTC ISO-8601 |

### `tasks`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK | Auto-incrementing; used in task branch names |
| `project_id` | INTEGER FK | References `projects(id)` |
| `title` | TEXT | Required |
| `description` | TEXT | Task instructions |
| `status` | TEXT | `TODO`, `CLAIMED`, `IN_PROGRESS`, `TESTING`, `IN_REVIEW`, `DONE`, `FAILED` |
| `priority` | TEXT | `LOW`, `MEDIUM`, `HIGH`, `URGENT` |
| `branch_name` | TEXT | Assigned once as `agent/{id}-{slug}` |
| `worktree_path` | TEXT | Legacy-compatible column containing the active repository workspace path |
| `created_at` | TEXT | UTC ISO-8601 |
| `updated_at` | TEXT | UTC ISO-8601 |

### `task_runs`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | INTEGER PK | Auto-incrementing |
| `task_id` | INTEGER FK | References `tasks(id)` |
| `started_at` | TEXT | UTC ISO-8601 |
| `finished_at` | TEXT nullable | Set at terminal pipeline state |
| `exit_code` | INTEGER nullable | Codex or test exit code; timeout uses a non-zero sentinel |
| `stdout` | TEXT | Agent and test output, phase-labelled |
| `stderr` | TEXT | Agent and test errors, phase-labelled |
| `result_summary` | TEXT | Concise pipeline result/failure reason |

Indexes cover task status/priority ordering and run lookup by task/time. Foreign keys are enabled.

## 4. State machine and worker flow

```text
TODO --atomic claim--> CLAIMED --> IN_PROGRESS --> TESTING --> IN_REVIEW --approve--> DONE
                               |              |
                               +--------------+-----------> FAILED --retry--> TODO
```

1. In a SQLite `BEGIN IMMEDIATE` transaction, select the highest-priority oldest `TODO` task and update it to `CLAIMED` with an `UPDATE ... RETURNING` guard.
2. Create a `TaskRun`.
3. Validate that the repository is clean, record its current branch, then create or reuse and check out `agent/{task-id}-{slug}`.
4. Persist the branch/workspace fields and set `IN_PROGRESS`.
5. Call `AgentExecutor.execute(task, workspace, signal)` with a backend-generated prompt and a timeout.
6. On agent success, set `TESTING`; `TestService` detects a supported project type and generates a fixed executable/argument list.
7. The backend checkpoints any file changes on the task branch and restores the original branch, whether execution succeeded or failed. It never merges or pushes.
8. Test success sets `IN_REVIEW`. A missing supported test configuration is reported as a test failure rather than silently treating untested code as verified. Any Git, agent, timeout, or test failure sets `FAILED` and finalizes the run.
9. The Worker immediately polls for the next task; review is not part of the worker loop.

On application restart, orphaned `CLAIMED`, `IN_PROGRESS`, and `TESTING` tasks are marked `FAILED` rather than silently rerun. A user can then inspect logs and explicitly retry.

## 5. Process and security boundaries

- The API binds only to `127.0.0.1` on a dynamically assigned port.
- Electron waits for database migration, API listening, and Worker start before loading Angular.
- Electron uses `nodeIntegration: false`, `contextIsolation: true`, and renderer sandboxing; no preload injection is needed.
- In production Express serves the compiled Angular UI from the same random loopback origin. During development Electron passes the random API URL to the Angular dev page in the query string.
- Project paths are canonicalized and Git-validated by the backend.
- Git, test, and Codex executions use fixed commands plus argument arrays and never use `shell: true`.
- Authentication remains the responsibility of the installed Codex CLI; this application stores no token or password.
- The worker requires a clean checkout, switches to the task branch before Codex runs, checkpoints task changes there, and restores the original branch afterward.
- The worker never merges task changes into the base branch and never pushes.
- Approval changes only task state; it does not merge branches.

## 6. API surface

Required routes:

- `GET /projects`, `POST /projects`
- `GET /tasks`, `GET /tasks/:id`, `POST /tasks`, `PUT /tasks/:id`, `DELETE /tasks/:id`
- `POST /tasks/:id/retry`, `POST /tasks/:id/approve`
- `GET /tasks/:id/runs`

Additional operational route: `GET /health`.

The Angular board polls `GET /tasks` so worker-driven state changes appear without introducing WebSockets in the MVP.

## 7. Deliberate MVP limits

- One local Worker and one task at a time.
- No automatic merge, PR, remote access, authentication, notifications, dependency graph, or cloud state.
- Test commands are detected from known project files; arbitrary command strings are not accepted from the UI/API. A repository with no recognized test runner goes to `FAILED` for explicit review.
- Deleting a task is blocked while it is executing. Git task branches are retained to avoid destructive loss of agent work.
